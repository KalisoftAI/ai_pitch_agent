# Kalika Outreach - Master Guide

Single source of truth for the Sales / Outreach workspace (FastAPI + React, deployed on Cloud Run).
Supersedes the previous loose set of Markdown notes (roadmap, deploy runbook, feature logs, integration notes).

## 1. What the app does

Kalika Outreach is an internal sales workspace:

- **Contacts** - imported sales contacts (Excel/GCS), searchable, de-duplicated, filtered by funnel data.
- **Marketing Companies** - step workflow: pick contacts -> choose channel -> personalise -> preview -> send -> track.
- **Templates** - email (HTML) and WhatsApp/WeChat (plain text) message templates, GCS + Excel import.
- **Campaigns** - one campaign per channel per send, with review/approve, retry, and per-recipient tracking.
- **Insights** - campaign analytics (sent/opened/failed/pending by day, channel, campaign, contact group).
- **Email connections** - Gmail OAuth / IMAP+SMTP mailboxes, sync status, retention, test send.
- **Field desk / Visits** - visit history, voice notes, rate calculator shortcuts.
- **Sales BI, KPIs, Feedback, Scheduler, UAT & ops** - adjacent modules in the same shell.

All user-facing strings are ASCII. No mock campaign data is generated by the app; analytics are computed from
`Campaign`, `CampaignMessage` and contact tables. The only curated data is the optional "Load sample records"
button on the visits screen, which inserts a short built-in sample set for format review.

### Key behaviours

- **HTML safety**: WhatsApp and WeChat templates/campaign bodies must be plain text. The API rejects HTML
  (`looks_html`) on template create/update, campaign create and send. The UI mirrors this with a
  "WhatsApp cannot send HTML" panel (pick a WhatsApp template / convert to plain text / save as template).
- **Personalisation**: `{{contact_name}}`, `{{company_name}}`, `{{product_name}}`, `{{designation}}`, etc.
  `render_resolved` substitutes per contact with readable fallbacks ("there", "your organization", "Team") and
  strips any leftover `{{...}}` tokens before sending. The composer flags unresolved tokens during preview.
- **Tracking**: emails embed a 1x1 pixel pointing at `/api/campaigns/track/open?...` using the request base URL
  (so HTTPS in production). Opens set `CampaignMessage.opened_at`; the dashboard reads opens from
  `campaigns/analytics` `opened` totals.
- **Channel counts**: "Sent" on the dashboard means accepted email + WhatsApp messages across all channels;
  "Opened" means tracking-pixel opens. Pending = approved-but-not-yet-accepted.
- **Selection**: the contact table supports "Select page", "Select all matching (N)" (server-side
  `/marketing-companies/ids`), group select, and duplicate removal. Selection is validated per channel:
  email sends only to valid emails, WhatsApp only to valid mobile numbers, "both" uses the union.
- **IDs are never silently truncated**: explicit `contact_ids` on campaign creation are all used; the old
  `.limit(filter.limit)` truncation was removed.
- **Route ordering**: `GET /campaigns/analytics` is declared before `GET /campaigns/{campaign_id}` - otherwise
  FastAPI matches the path param route and returns 422.

## 3. Local development

```powershell

C:\Python314\python.exe -m uvicorn sales_fastapi.main:app --reload --port 8000
```

```powershell

```


`CLOUD_SQL_CONNECTION_NAME`. Alembic: `alembic upgrade head`.

## 4. Auth and access

- Google Sign-In (`/auth/google`) for allowed domains/emails, plus a password route (`/auth/password`).
- Tokens are stored in `sessionStorage` (`sales_token`). `request()` in `main.jsx` clears the token and emits
  `auth-expired` on 401, returning the user to sign-in.
- Roles gate admin-only operations (imports, sync, UAT).

## 5. API map (high level)

- `POST /auth/google`, `POST /auth/password`, `GET /auth/me`
- `GET /config`, `GET /health`
- `GET /marketing-companies` (filters: `q, category, call_status, funnel_stage, sales_progress, due_follow_up,
  requirements_only, has_phone, has_email, missing_email, missing_phone, ids, sort, limit, offset`)
- `GET /marketing-companies/count`, `GET /marketing-companies/ids` (for select-all-matching)
- `GET /marketing-companies/stats` (cached), `/activity`, `/duplicates`, `/segments`, `/sources`
- `POST /marketing-companies/import`, `/sync`; `PATCH /marketing-companies/{id}`
- `GET/POST /templates`, `PATCH/DELETE /templates/{id}`, `/templates/meta`, `/seed`, `/sync-gcs`,
  `/sync-specific`, `/import-whatsapp`, `/upload`
- `POST /campaigns`, `GET /campaigns`, `GET /campaigns/analytics?days=N`, `GET /campaigns/{id}`,
  `/campaigns/{id}/preview`, `/approve`, `/send`, `/retry`, `GET /campaigns/track/open`
- Email: `/email/connections`, `/email/sync`, `/email/sync/state`, `/email/sync/analytics?days=N`,
  `/email/retention`, `/email/test-send`, default-connection endpoints
- Visits: `GET /visits`, `POST /visits/samples` (built-in sample records only)

## 6. End-to-end workflow (manual test script)

1. **Insights** (`MarketingCompanies` -> Insights tab): tiles for Sent, Opened, Failed, Pending, Campaigns;
   daily chart with email/WhatsApp/failed/opened; channel and campaign breakdowns; Refresh button.
2. **Contacts**: filter by group/status, search; check "Select page", "Select all matching"; confirm the
   sticky summary shows selected count + email-ready + WhatsApp-ready; "Remove dupes" only affects real dups.
3. **Templates**: pick a template, "View" opens an email iframe preview or a WhatsApp bubble; "Edit" edits the
   raw stored body (channel-aware select; HTML is blocked for WhatsApp/WeChat on save).
4. **Personalisation**: composer replaces variables in the first selected contact; unresolved tokens and
   missing subject/recipient are flagged before send.
5. **Preview**: correct channel labels, HTML-not-allowed warning for WhatsApp, total approved count.
6. **Send**: "Send now" sends immediately (auto_send), "Send for review" leaves the campaign pending.
   Both-channel sends create two campaigns.
7. **Analytics**: campaign detail shows per-message status, sent/viewed timestamps and errors; retry failed.

  `migrations/versions/0012_mail_sync_state.py` would fix it; deferred while avoiding unnecessary migrations.
- CI already fails on unrelated pre-existing lint/coverage issues.
- MarketingCompany has no `designation` column in the DB; the UI shows `-` rather than inventing one.
- The live Kalika Sales Tracker feed is not wired; the visits sample button inserts curated records only.
- Visits, Scheduler and UAT modules are functional but outside the core outreach workflow.
